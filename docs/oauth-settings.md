# OAuth 设置的读取与保存

第三方登录配置存放在 `system_settings` 的 `auth.oauth` 行中，使用现有
settings encryption key 加密。服务端会解密使用；管理界面响应只提供
`hasClientSecret`，不返回 secret、密文或加密参数。

只有配置行不存在时，读取才返回四个受支持供应商的未配置默认值。
数据库读取失败、解密失败或已存内容格式无效，都表示配置暂不可用。
已存内容必须是包含 `providers` 对象的配置，不能用 `null`、缺少
`providers` 的对象或错误字段类型作为默认配置。

登录开始、OAuth 回调、管理配置概览和配置更新遇到上述读取错误时，
返回 HTTP 503 和稳定错误码 `OAUTH_SETTINGS_UNAVAILABLE`。响应不包含
底层数据库、解密错误或凭据信息。此时不会创建 OAuth 状态 cookie、
发起供应商请求或把空默认配置保存回数据库。

`PUT /api/v1/admin/config/oauth` 继续沿用原有管理权限和请求格式：

- 未提供或留空 `clientSecret` 时，保留该供应商已存的 secret。
- 未列出的供应商保持原配置；提供非空 secret 时，只替换对应供应商。
- 首次配置允许在没有 `auth.oauth` 行的情况下保存；启用供应商仍须满足
  原有完整配置和回调 URL 校验。
- 同一次请求中，去除首尾空白并转为小写后重复的供应商键返回 HTTP 400，
  不以 JSON 对象的遍历顺序选择其中一个配置。

读取、合并、加密和写入在同一数据库事务中完成。事务先取得
`settings:auth.oauth` 的 advisory lock，使不同服务实例和首次插入遵守
同一保存顺序。事务内读取使用已持有的连接，不再从连接池获取第二条
连接；读取或写入失败会回滚，成功提交后才返回已脱敏的配置。

本次变更无需迁移，也不改变登录回调、供应商停用、账号关联或权限政策。
不可读的旧配置不会被自动覆盖或清空。应先修复数据库访问、加密 key 或
经过明确授权恢复有效配置，再重试保存；本次任务没有修改生产设置。

隔离 PostgreSQL 回归覆盖：真实 SQL 读取错误后禁止覆盖、错误 key、
无效配置格式、缺失行首次保存、省略和替换 secret、保留其他供应商，
以及概览、登录入口、回调的失败响应。测试使用合成凭据和受控 HTTP
transport，单连接池验证事务不会重入连接池。它们不证明真实供应商
连通性、生产密钥可用性或生产 OAuth 配置健康。
