## 同条件测量

- 首页的首条模组标题位置（桌面 1365×840、手机 390×844）分别由 701→471 和 908→449 CSS 像素。后台总览初始管理请求由 4 个降至 1 个。两次都是同一组合成响应和生产版 Chromium 页面。原图、概念图与改后实拍见 frontend 的 `docs/ui/README.md`。
- PostgreSQL 18.6 的相同会话中建立 PERF036 的百万项目数据。按交替顺序对每个查询各跑三次 EXPLAIN ANALYZE。以毫秒计，数据库执行时间中位数为稀有词 2437.155→2.269，精确 ID 3302.275→1.400，普遍命中词 0.164→0.647，无结果 6.261→5.298。广泛命中需要额外的小样本探测。本机合成数据的结果不用于估算线上时延。
- 后台翻译管理在 5,103 个词条下，单页编辑框由 5,103 降至 50。同一 Chromium 的三个新页面从点击到可编辑分别用时 6061/8169/5238→650/123/124 毫秒。现有分页组件保留筛选、人工草稿与批量翻译范围。
- 70 个长导入排在通知前。基线 3.5 秒内未开始通知。相同合成负载的修订版一次用时 801 毫秒，首项导入仍在执行，其余 69 项保留待办。持久 JetStream 的 300ms ACK 窗口覆盖 900ms 工作时，正常续约将入口执行由两次降为一次。[队列设计、任务表与测量](../OUTBOX_JETSTREAM_DESIGN.md)
- 同一真实 Fabric 世界与资料输入，世界生成由一次 620 毫秒的步骤拆为 694 步，最终实测最长 98.792 毫秒，阶段墙钟 650 毫秒。37 个非 manifest 成员逐字节一致。12 毫秒为软预算，单对象 codec 与其余需要游戏上下文的步骤仍可超时。

## 保留的边界

- Go 1.26.11 的 `govulncheck` 结果为零符号命中，另有五个模块层公告。Next 16.4.6、sharp 0.35.5 更新后，npm audit 仍报告四条低危依赖路径，来自同一 KaTeX 公告。exporter 查询了 52 个坐标，Minecraft 1.20.1 的十个宿主库共匹配 24 个公告。本次未在发布 JAR 中建立这些公告的直接可达路径。另七个直接依赖坐标在本轮查询无匹配。[安全审查](security-review-2026-11.md)
- 浏览器验证使用真实 Chromium 及桌面和手机视口。有头 Chromium 正常连续打开原版火把资料和配方，55 次媒体请求对应 55 个不同资源。默认无头 Chromium 被识别为爬虫，收到 429 后按响应的 Retry-After 等待再打开同一配方，像素检查通过。OAuth 同一字段的两次显式提交按数据库锁的提交顺序生效。云 OSS、真实 OAuth 和付费供应商账单、实体手机/显卡及多节点 NATS 集群属于部署环境的验证范围。
- 历史超限冷词典仍须在有权限的对象存储连接中核对解压字节，有本地原包的编辑者可重新上传并走原审核流程。JEI 类别重组和部分资料标准化也仍在数据库事务中，实际耗时依输入而定。普通站内目录、可编辑的八种语言和冷语言读取需要分别核算。
- 发行 JAR 单独核对 SHA。Fabric 在独立标准加载器中发现 exporter 与 JEI。该预检停在图形初始化。标准启动器没有已授权的离线会话，Forge 离线安装器缺少启动器配置及其清单的 13 个安装依赖和一个运行库。两种发行 JAR 的独立启动器入世界验收仍开放。
- 此批变更沿用 PostgreSQL generation 168、既有公开 ID 和导出协议。历史原包、人工资料和上线运行中的任务仍由原有归属及版本规则处理。已有 JetStream 使用运维设置，新建 stream 采用 256 MiB 且满时拒收。若主流与死信均满，应依恢复手册释放容量并核对事件、任务和供应商回执。

## 发布、回滚与恢复

1. 记录当前的应用镜像、Go/Node/JDK 版本、数据库 generation、加密密钥版本、三方公开 origin，以及管理面板显示的 stream 及未交付/死信数。备份 PostgreSQL，用独立实例试恢复。保留对象桶、NATS 持久卷、账号和进行中的任务。工作分支上的提交供评审后发布。
2. 先发布后端与 Worker，使用 go.mod 指定的修订版编译器。先核实 /ready、公开目录、各管理配置的授权读取及无权账号的 403。旧前端仍能按原聚合接口读取设置。确认新版鉴权节点均能返回会话标记、接受条件退出及 OAuth 字段 PATCH 后，再发布前端。更新全部提供认证的 API 副本后，时间限定权限的缓存修复才全面生效。如需在更新期间维持严格的到期边界，把流量集中到新版鉴权副本。核对 outbox 最老未交付年龄、重试、stream 空间及死信，再恢复日常任务流量。
3. 用相匹配的前后端 origin 构建并发布前端，检查一次真实分类搜索、退出、后台单面板重试和公开 PNG 重定向。失败的私有配置应显示重试。使用两个身份验证独立审核，公开浏览器验证图片像素与目录。成功上传的 ZIP 在状态页应能区分导入和审核。
4. exporter 分发可独立进行。保留支持的 v1 manifest、v7 JEI 和历史包兼容规则，记录新包 SHA-256、生产提交及加载器。按两个加载器分别登记最终构建、真实产包与公开展示结果。
5. 回滚时优先回退前端或客户端 Mod。遇到后端问题先把流量收回到验证过的副本，保留 DB、WAL、队列与对象。全面回退至旧 API 会恢复旧权限、图片和队列行为，需要运维评估后执行。服务端暂时停用消费者须保留数据库发件箱。NATS 断开时先确认现有本地配送与数据库租约，当目标状态不明，先定位 event_id/任务/供应商交付记录，再通过权限受控的恢复入口重试。[队列恢复手册](queue-recovery.md)
6. 配置读取失败先检查部署时的设置加密密钥、连接和真实存储内容。保留原密文并用相应密钥恢复。在隔离副本验证后再处理遗留设置。已被业务事务墓碑标记的原包需等待签名到期、引用检查和对象删除任务。未知计费或邮件交付需要核对供应商记录，再决定人工恢复。[文件字节绑定](audit-oss-byte-binding-upgrade.md) · [翻译结算](ai-translation-reliability.md)

环境私密文件、浏览器 cookie、预签 URL 和原始调试日志不随发布物分发。
