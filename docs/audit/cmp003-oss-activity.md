# CMP-003: OSS upload registration and existing activity

This batch preserves the existing production request activity classification. `inferredActivityAction` treats upload routes as `upload`, and the ordinary/admin OSS routes map to `file`; scan and OSS configuration writes map to `edit/file`. Import/project wrappers keep their existing route classification through `enqueueRequestActivityTx`. No new annotation or reward definition is introduced. Direct callers without a request activity annotation still create no activity event. The production runtime supplies the activity monitor; the transaction producer no longer depends on a successful post-response enqueue.

Remote HEAD/GET, actual source SHA-256 verification, image processing, converted-byte hashing and access signing precede registration locks. A transaction then serializes the object key, locks fresh blueprint/cover associations before quota, settles a new user reservation, registers the verified file, binds any blueprint/variant/cover, enqueues its normalization job and NATS intent, and persists the original durable activity intent. It commits these facts together. Scan status, dependent project/evidence state and audit now share the scan transaction with the original activity; OSS configuration uses its existing settings transaction.

Already registered files are already represented in quota buckets. Concurrent/repeated completion releases only a remaining reservation and does not count another file or activity. A completed concurrent request receives an idempotent200. Reverification of an unverified legacy ordinary file keeps its prior201 response, while repaired report metadata retains the existing idempotent200 behavior. Historical files do not authorize guessing a missing reward. Actual source and stored hashes are retained on fresh and repeated responses.

`completeBlueprintUpload` remains a standalone transactional wrapper; `completeBlueprintUploadTx` leaves commit to its caller. The blueprint-only32MiB limit now applies after matching a real blueprint, preserving ordinary/admin64MiB upload support. Clean baselinefd25ce3 returns the specific blueprint-limit413 for a valid33MiB ordinary ZIP in both roles; the fixed handler accepts those files and still rejects an oversized actual blueprint at presign. No blueprint limit was enlarged.

The failure tests use actual HTTP and PostgreSQL, with only an owned OSS protocol provider. Unavailable activity storage gives the specific500 and leaves file, quota, reference, job, asset metadata and outbox facts unchanged. Recovery creates one intent. Controlled concurrent source-hash GET barriers observe zero acquired connections in the two-slot registration pool, then produce exactly one file/intent/quota contribution. Scan rollback and quarantine retain two existing FK references. A real decodable losslessWebP fixture preserves the PNG pixels/alpha; after an activity failure, source and converted bytes remain retryable, recovery stores their distinct actual hashes and correct quota, and completion replay creates no second intent.

The first full related race run passed core scopes and all TEST036/037 neighbors. Additional large-file, converted-retry and precise registration cases passed. No PostgreSQL/pool/time budget was raised, and the evidence does not infer exclusive-host root causality from a successful retry. The old BUG080 guessed schema lacked new hash columns and allowed an arbitrary first500; it now installs the actual migrated isolated schema and proves the specific injectedXX001 evidence-metadata boundary.
