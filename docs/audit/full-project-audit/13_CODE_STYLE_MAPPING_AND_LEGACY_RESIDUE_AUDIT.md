# 代码风格、映射与旧残留专项审计

## 方法

本专项同时使用全仓关键词、声明/调用搜索、路由注册、构建、严格未使用检查、Git 历史和新旧实现语义对照。函数仍有调用方不代表它不是旧实现；反之，名称包含 `legacy` 也不自动代表可删除。

统计只包含确认问题，不把关键词命中数、格式化输出行数或合理的协议适配器计为问题。

## 风格一致性矩阵

| 领域 | 当前主要风格 | 不一致实现 | 权威建议 | 处理级别 |
| --- | --- | --- | --- | --- |
| Go 格式 | gofmt | 14 个文件未格式化 | CI 要求 `gofmt -l` 为空 | 必须修正 |
| Handler 命名 | 业务动词/对象 Handler | 未发现造成职责误解的第二套主流 | 保持现状 | 可以保持 |
| API 字段 | camelCase JSON DTO | 自动更新响应 snake_case | 统一明确响应 DTO | 逐步统一 |
| 错误返回 | 稳定错误结构 | 局部直接中/英文字符串 | 错误码 + i18n | 必须修正关键路径 |
| 时间 | PostgreSQL timestamptz/UTC，前端按 locale 展示 | 未确认第二套存储时区 | 保持 UTC 边界 | 可以保持 |
| 项目类型 | 后端注册/白名单，前端边界类型 | 显示层存在有意别名 | 不合并业务不同类型 | 可以保持 |
| 前端请求 | 统一 API 客户端 | 未确认组件直接绕过认证层 fetch | 保持统一客户端 | 可以保持 |
| 缓存键 | 版本化、业务前缀 | 未确认旧权限键仍读写 | 保持版本化键 | 可以保持 |

## 新旧实现并存结论

确认四类：

1. 通知模板路径与直接固定文案路径并存；调用方行为不同，属于发布前问题。
2. 新旧未读路由并存；逻辑相同，是否删除取决于外部客户端证据。
3. Argon2id 与旧 PBKDF2 验证并存；当前新数据只写 Argon2id，但旧读取没有升级或移除策略。
4. 目录排序的旧单值枚举和新字段+方向模型并存；前后端都保留转换层。
5. Mod导出任务的PostgreSQL Outbox权威路径与关闭Outbox后的Core NATS/进程goroutine旧路径并存；这是内部开发配置，不承担外部兼容。
6. 外部元数据导入在默认Outbox模式下仍同时运行数据库queued扫描并通过Core NATS直发；两个发布入口依赖job状态claim去重，但可靠性和监控事实分裂。
7. Mod资料单板块PUT与整版layout并存；前端已经只使用layout，但旧路由仍可持久化跨版本子树并按不同所有权字段拒绝资源。

未确认存在旧权限缓存 Key、数据库新旧字段双写、旧前端 API 客户端或旧组件仍服务边缘页面；已确认元数据导入在同一默认配置下同时保留Outbox发布和旧Core NATS数据库扫描发布，任务claim降低重复执行但没有消除双入口。

## Git 历史结论

模板通知系统晚于部分直接通知实现加入；后续新增功能也有调用方未收口，因此不能把固定文案函数视为“仍被调用所以是权威”。兼容报告明确给旧未读路由赋予外部客户端责任，因此也不能因为本仓库无调用就直接删除。

### 必须保留的外部格式映射

`catalog-resource-identifiers.ts`仍需读取导入/模板Schema中的短资源种类，`loot-table-model.ts`仍需读取旧导出包的`definition`包装。这两处位于外部或持久格式边界且增加了真实格式转换，不计为无意义映射。只有在格式版本化、所有生产者迁移且历史包不再被接受后才能删除。
