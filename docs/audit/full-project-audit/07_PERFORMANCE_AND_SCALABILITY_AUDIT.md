# 性能与可扩展性审计

## 已确认热点

### 编辑员申请列表 N+1

`project_editor_application_handlers.go` 在取得申请列表后逐条调用项目名称查询。附件已经批量加载，但项目名称仍为每条一查。列表上限越大，数据库往返线性增长。

建议按 `project_type + project_id` 收集唯一键，分类型批量查询后在内存关联。修复前后记录 SQL 数量和接口耗时。

### 用户项目陈列反向扫描全站项目

`profile_showcase_handlers.go:L157-L196` 先 UNION 全站所有已发布 Mod、整合包、简单项目、服务器、蓝图、皮肤和社区内容，再逐行执行两个 `effective_project_access` 相关 EXISTS，最后才过滤单个用户并限制 100 条。项目规模到百万级时，单个用户主页请求会评估大量无关项目，末端 `LIMIT` 无法提前缩小集合。

建议从 `effective_project_access where user_id=$1` 的用户小集合出发，按类型批量关联当前公开项目；使用 10 万、100 万和 1000 万项目合成数据分别保存 `EXPLAIN (ANALYZE, BUFFERS)`。

### 粉丝/关注深 OFFSET

`profile_handlers.go:L143-L163` 允许页码 10000、页大小 60，最高 OFFSET 约 599,940，且每一页都执行一次 `COUNT(*)`。大账号后部页面需要扫描并丢弃大量索引项。

建议改用 `(created_at, user_id)` 稳定游标；总数复用可信计数或低频缓存，不要让每次翻页都重新扫描计数。

### Markdown差异算法按请求上限放大

`activity.MarkdownDeltaBytes` 为两份文本总字节数分配 `2*N+3` 个 `int`，并在回退前最多迭代8192层编辑距离。全局JSON上限为8 MiB，两份接近上限的文本在64位进程可产生约256 MiB单请求临时分配；完全不同文本还会带来高CPU。评论、作者说明和服务器正文编辑均调用它。应设置领域正文上限，大文本走线性/近似统计，并增加内存/耗时基准。对应 `SEC-007`。

### 成功写请求的无界后台goroutine

反滥用中间件为每个成功变更启动一个goroutine，使用 `context.Background()` 执行内容规范化、事件/指纹和清理SQL。没有有界队列、并发上限、截止时间或关机排空；数据库变慢时会积累goroutine并争夺业务连接池。应改为有界批处理/可靠队列，并在数据库故障下压测。对应 `PERF-004`。

### 活动清理预览重复聚合

大范围手动清理预览会对同一候选集执行总COUNT、三个维度GROUP和样本查询共五次扫描；千万级活动表上会造成管理员触发的I/O尖峰。危险标志是在全部查询之后才计算。建议预估/后台化并合并聚合，对三个数据规模保存实际计划。对应 `PERF-005`。

### 合成类型列表逐项查询催化剂

`global_catalog_handlers.go:L80-L95` 在最多60个合成类型的循环中逐项调用 `catalogRecipeTypeCatalysts`；后者在 `catalog_editor_handlers.go:L1507-L1556` 每项执行一次权威催化剂查询，没有数据时再执行一次导入快照回退查询。一次列表请求因此产生主查询之外最多120次数据库往返，缓存未命中或数据版本变化时会集中放大。应把类型ID批量传入一次加载催化剂和回退快照，再按类型分组。对应 `PERF-006`。

### 公开目录缓存命中前仍全量计算数据版本

`writeCachedCatalog` 在读取缓存前先构造 `latest_revisions` 并对全部最新修订执行有序 `string_agg`，同时查询目录实体和内容修订的最大时间。所有公开目录请求即使最终命中缓存，也必须先完成这次数据库聚合；目录规模增长后，缓存只能省去业务Loader，不能省去版本计算本身。应维护事务内递增的目录数据版本或可精确失效的版本指针，把O(全量修订)改为O(1)读取。对应 `PERF-007`。

### 合成详情逐槽读取候选项

`catalogRecipeBindingRows` 先查询全部绑定槽位，再为每个绑定调用 `catalogRecipeCandidateRows`。模板槽位虽有数量上限，但单个详情请求的SQL数仍随槽位数线性增长，最大配方会占用大量数据库往返。应一次联表读取绑定和候选项，按绑定ID/槽位在内存重组。对应 `PERF-008`。

`promoteImportedRecipeTemplatesTx` 先读取全部模板，再在激活revision的同一事务内为每个模板单独查询槽位。这是模板数量线性增长的1+N往返，并会延长活动修订切换事务。应一次批量读取并按模板分组。对应 `PERF-009`。

Mod导出Tag列表的 `all=1` 会把单次上限扩大到10000，Tag详情则无分页读取全部成员，再执行本地化装饰和JSON组装。活动revision的读取不限于后台，应改为稳定游标分页并将完整导出移到受控异步边界。对应 `PERF-010`。

### 巨型前端组件

`admin-console.tsx` 约 5,749 行。其渲染和状态并非一定慢，但任何局部状态变化更容易造成大范围重渲染，且构建/审查成本高。建议按后台业务面板拆分并使用现有数据 hooks，不创建元框架。

### 作者认领待审队列无分页且逐条读取附件

`admin-community-panels.tsx:L84-L96`一次读取并渲染全部作者认领；`creator_handlers.go:L485-L518`没有分页上限，并在每条认领循环中单独读取附件。积压N条时形成无界响应与`1+N`次数据库查询，证明Markdown和附件DTO还会同时放大传输及DOM成本。应以`created_at,id`游标分页，按当前页ID批量读取附件，并为每页约束SQL数量。对应`PERF-072`。

### 巨型 Handler

多个 HTTP 文件超过 1,500 行。主要风险是重复查询/事务边界难发现，不是单纯行数。拆分时优先抽出已有重复查询与领域操作，避免创建只转发 Repository 的空 Service。

## 数据库与列表

- 主要列表包含 limit/cursor/page 约束；未发现明显的无界全表返回公共接口，但“有上限”不代表深 OFFSET 或权限过滤顺序可扩展。
- 评论楼层定位使用目标对象和楼层索引，不需要逐页查找。
- 全局资源绑定、日志历史和导出任务均使用分页结构。
- 远程集成测试包含外键索引检查并通过。

没有代表性生产数据，因此没有把静态索引存在等同于查询计划最优。现有文档也明确将大表分区决策推迟到真实 `EXPLAIN ANALYZE` 数据后，这是合理做法。

仓库负载脚本和全部已提交JSON结果已逐行复核：请求总数、状态分类和场景计数彼此一致，但目录测试使用空业务表，查询脚本只测`OFFSET 20`或任意首位用户，反滥用计划没有`ANALYZE/BUFFERS`。此外负载器会把预期403/429算为错误、把小于0.5%的真实失败四舍五入成0，并在每个请求重新构造请求池（`TEST-050`）。因此这些结果只能证明对应开发样本，不能降低本文百万级查询风险的评级。

## 缓存

- 权限缓存键包含用户权限、RBAC 和项目 ACL 版本，不依赖 Redis `SCAN` 大范围失效。
- 共享版本指针变化时绕过本地旧缓存。
- Redis 故障时权限回源数据库，安全优先。
- 旧版本缓存键依靠 TTL 自然过期，避免批量删除。

需要在多实例环境测量：版本指针读取开销、RBAC 命中率和 Redis 故障时数据库压力。

## 异步任务

数据库任务/Outbox 避免在项目更新事务内同步遍历全部关注者。收藏夹导出和项目更新存在数据库扫描器兜底，但本机 JetStream 未启用，无法验证正常消息路径性能和重试行为。

活动Outbox只保证原始活动写入；成长任务投影发生在活动事务提交和Outbox删除之后，失败只记录日志，没有投影游标或自动重放。因此“可靠活动记录”不能等同“可靠成长进度”，详见 `ARCH-006`。

## 文件和日志

- ZIP 与日志处理设置尺寸、文件数、解压比和内容限制。
- 大文件由存储/分块接口处理，公开日志页面不会把未处理原文件直接渲染为 HTML。
- 仍需在真实 OSS/大文件环境验证内存峰值、Range、并发脱敏和临时文件清理。

## 缺失的性能证据

- 仓库没有 Go benchmark。
- 未发现固定的大数据量性能测试数据集。
- 未执行生产规模 `EXPLAIN (ANALYZE, BUFFERS)`。
- 未执行多实例 Redis/NATS 压测。

## 已复核的前端请求放大

旧 `/health` 高频轮询在当前代码中已不存在。`site-shell.tsx:L165-L215` 只在后端被判定不可用且页面可见时请求 `/ready`，使用 5/10/20/30 秒退避；恢复后停止。未读汇总在 `L279-L297` 首次加载并每 5 分钟刷新，页面不可见时跳过，同时允许事件触发更新。该实现不是持续数据库健康轮询残留。

仍存在任务页 2.5～3 秒状态轮询，但集中在用户正在查看的导出/蓝图处理状态；本轮未确认全站后台高频轮询。后续应优先复用 SSE/现有实时连接并在页面不可见时暂停。

## 建议性能基线

1. 对登录、权限解析、项目列表、评论创建/定位、用户卡片、未读汇总建立 p50/p95/p99。
2. 对编辑员申请列表修复前后记录 SQL 数。
3. 对 10k/100k 关注者事件执行批处理和幂等重试测试。
4. 对日志和 ZIP 使用接近上限的安全样本测内存与耗时。
5. 基于远程测试库规模执行查询计划，而不是仅按索引名称判断。

## Mod 导入与公开目录新增风险

- 活动导出revision的资产索引无分页/字节上限，路径模式和完整模式都会把全部资产读入内存后一次编码，见 `PERF-011`。
- Tag列表的 `all=1` 可返回10000项，Tag详情成员无服务端上限；前置通配搜索也无法直接利用普通B-tree，见 `PERF-010`。

## 审核队列新增风险

`contentReviewQueueQuery` 对十余种待审来源执行巨型 `UNION ALL`，仅以创建时间排序并固定 `LIMIT 2000`。关键词、类别、操作、项目类型、分面和API分页全部在Go内存中完成。该实现既让第2001条后的任务不可达，也使数据库必须为每次请求组合宽行候选集；积压达到十万或百万级时，固定截断掩盖了真实总量而没有解决查询扩展性。应建立可索引的统一审核投影，使用数据库过滤和游标分页，并分别计算可见范围内的准确分面。对应 `BUG-021`、`PERF-012`。

Mod修订历史同样没有分页，且每行通过多个相关子查询重复取得审核事件和关联用户；前端一次渲染完整历史。应改为游标分页并一次联接最新审核事件，见 `PERF-013`。

Mod详情先读关系组，再按每个组查询关系项；合法请求最多50组，因此一个公开详情可附加50次数据库往返。应一次联接并按组聚合，见 `PERF-014`。

## Mod资料目录与布局扩展性

- 匿名板块资源接口保留深OFFSET，并可用 `all=1` 一次返回20000个带本地化、图标、definition和派生引用的宽对象；COUNT与数据查询都包含递归子树、前置通配和相关子查询，见 `PERF-015`。
- 资源发布同步未解析引用时逐标识查询并逐条插入；单字段可达500个标识，多个字段会在同一事务产生上千次往返，见 `PERF-016`。
- 权威整版布局已批量读取和写入资源placement，但新分类/相似组ID仍逐个查询，分类及本地化也逐项写；上限输入可产生数千至上万SQL，见 `PERF-017`。
- 旧单板块PUT还允许20000资源并在循环中为每项查询版本、查询资源、删除旧placement和插入新placement；没有第一方前端调用，应该迁移删除而不是再单独优化（`LEGACY-007`）。
- PNG上传池并发固定为8，但整个导入允许最多200000个ZIP条目、8GiB解压数据和512MiB单文件；HTTP已异步化，仍需以接近上限的包实测Worker峰值内存、临时文件和OSS吞吐。
- 导入内容同步在同一事务执行多次板块/布局查询与写入；并发激活会碰撞ordinal并扩大重试与锁成本，见 `BUG-017`。

## 简单项目目录与作者关系写入

- 插件、地图、材质包、光影、数据包和附属资源共用的目录接口在100项上限内加载每项全部语言的完整Markdown正文、作者团队成员、图库和父项目；整合包目录也返回完整1MiB正文、最多2000个包含模组、全部作者团队成员和图库。单次匿名响应可达数百MiB，并触发包含模组逐项LATERAL解析，见 `PERF-018`。
- 简单项目和整合包发布无论作者关系是否改变，都会删除全部关系并逐条重插。statement级ACL触发器因此按关系数反复递增全局版本，并逐行制造搜索同步事件，见 `PERF-019`。
- 目录仍使用精确COUNT与OFFSET；`ILIKE '%query%'`、数组和EXISTS筛选在百万项目级需以真实分布执行 `EXPLAIN (ANALYZE, BUFFERS)`。搜索索引只在未使用其他筛选时接管分页，组合筛选仍全部落回PostgreSQL。
- 已批准整合包创建在revision创建前后完整执行两遍关联替换，最多2000个模组的解析、插入和未解析引用处理被同步放大，见 `PERF-020`。

## 服务器目录与主动探测

- 目录允许到第10000页，最大约60万OFFSET；组合筛选落回PostgreSQL的精确COUNT和相关EXISTS，百万级风险见 `PERF-021`。
- 后台服务器审核列表固定读取最多200条完整正文，并为每条串行读取证明附件、链接和模组，单次请求最多形成 `1 + 200 * 3 = 601` 次SQL，见 `PERF-022`。
- 项目文件接口无分页地读取全部站内文件、全部Modrinth版本并最多读取500个CurseForge文件，再合并排序和返回；高版本数项目会产生大响应，见 `PERF-023`。
- 项目更新日志接口同样无分页，并为每条聚合最多8份、每份20万字符的正文后一次返回；多年更新项目存在大JSON与数据库聚合风险，见 `PERF-024`。
- 项目更新通知每200人执行一次按event的通知总数统计，但唯一索引以recipient开头，不能支持该反向查询；每批还逐人插入，见 `PERF-025`。
- 状态探测固定8秒，Configuration探测最长30秒且每次最多512个2MiB包；缺少全站主动探测并发信号量的证据。Fabric注册表累计64MiB并可物化500万字符串，内存风险见 `SEC-014`。
- 在线历史最多90天，按默认5分钟探测约25920点；查询有 `(server_id, checked_at desc, id desc)` 索引，但API不降采样且一次返回全部点。若调度频率降低或清理正常，该量尚可；仍应为移动端提供时间桶聚合并验证清理任务。
- 嵌入图标目录虽按250条分批、8路并发处理，但每条图像在像素检查前完整解码；单图可接近400MiB解码内存，并发峰值远高于128MiB请求/源文件限制，见 `SEC-010`。
- 自动镜像对每个外部文件执行 `io.ReadAll`，单文件上限256MiB，再从同一字节切片校验哈希和上传OSS；缺少全站任务并发预算，多实例内存峰值会线性叠加，见 `PERF-026`。应改用受控临时文件/流式哈希上传并设置全站信号量。
- 爬虫候选后台固定按下载量返回前100条完整JSON payload，没有游标或offset；候选表持续累积后，其余记录在同一状态下不可达，且大payload增加响应。运行列表同样只提供最新100条。见 `PERF-027`，应使用稳定 `(downloads,id)` / `(created_at,id)` 游标和摘要/详情拆分。
- 通知列表最多200条、无游标，旧通知不可达；`read-all` 对用户全部历史定向通知和全站广播执行一次无界 `insert ... select ... on conflict`，用户首次操作可产生大量receipt写入（`PERF-028`）。应使用稳定时间/ID游标，并以用户级read watermark表达“此前全部已读”或分批处理。
- 未读对账按活跃用户游标分批，但SQL对每个用户分别执行通知COUNT和私信COUNT；广播通知部分事实相同却被每名用户重复扫描。百万用户周期性全扫会持续放大数据库负载（`PERF-029`）。应维护可靠增量计数/广播watermark，只抽样或按漂移信号回算。
- 私聊会话列表无分页，并对每个会话执行一次最近消息LATERAL和一次未读相关COUNT；未读索引没有以会话ID组成有效前缀。消息读取按 `id desc`，Schema却只有 `(conversation_id, created_at desc)`，长会话不能稳定利用排序索引，且更早于最新100条的消息没有API游标（`PERF-030`）。应改为会话 `(last_message_at,id)` 与消息 `(conversation_id,id)` 游标，维护/联接未读摘要并补匹配查询的部分索引。
- 前端每个SSE事件无条件派发 `mcmods-unread-change`；消息中心还监听原始事件。`message.created` 会触发外层会话加载、当前会话refresh中的消息+会话加载和Header未读加载，消息读取成功又派发一次未读加载；通知事件也重复请求未读摘要（`PERF-031`）。应由单一查询缓存按事件类型精确失效并合并同一tick请求，而不是跨组件自定义事件叠加fetch。

## 运行与审计日志新增风险

- 每个 `/api/` 请求在业务Handler返回后同步执行一次 `app_logs` INSERT，使用脱离请求取消的 `context.Background()` 和2秒超时。数据库降级时，每个请求仍可额外占用Handler goroutine至2秒；Presence、轮询和高频读接口也全部产生写放大（`PERF-032`）。应使用有界、可观测且按类别取舍的日志摄取队列；安全审计仍需可靠事实源，普通访问日志则可按策略采样。
- 后台日志查询只有最多500条的limit，没有游标，旧记录无法连续浏览；关键词对多列执行前后通配，其中包含 `payload::text`、邮箱和用户代理。百万级日志下既难利用普通B-tree，又会为每次搜索扫描/转换大量宽JSON。清理则在保存配置的HTTP请求里对每类表执行无批次上限的单条DELETE，可能制造长事务、锁和WAL峰值（`PERF-033`）。应增加 `(created_at,id)` 游标、受控全文/专用检索列，并按稳定ID批量清理。

## 热度与评分全量重算风险

- 每个需要刷新热度的项目都会重新聚合该项目全部浏览日桶、去重访客、收藏、评论、子资料评论、评分和维度评分；时间衰减调度还周期性把近90天有事件或近60天新建的全部项目重新入队。单项目历史达到百万行时，即使各谓词具备索引，反复全历史COUNT/SUM/DISTINCT仍会把后台Worker变成持续扫描器（`PERF-034`）。应维护可校准的增量累计事实，仅对短窗口趋势按日桶聚合，并用离线校准替代每次全量重算。
- `refresh_content_rating_global_stats` 对某类型的全部评分扫描时，每行调用PL/pgSQL `content_target_owner_id(route.id)`；该函数又查询公开路由和派生项目权限视图。它无法被SQL内联成集合联接，形成数据库内部的相关逐行权限解析，且全局统计最频繁每5秒按类型重算一次（`PERF-035`）。应一次集合联接全部有效开发者关系或预先构造排除集合，并按变化增量维护全局评分统计。

## 后台项目目录分页风险

- 后台项目列表每次先执行精确 `COUNT(*)`，名称搜索使用前后通配 `ILIKE '%q%'`，结果页使用无上限OFFSET并按派生热度、更新时间和路由ID排序（`PERF-036`）。项目达到百万级时，深页会重复扫描/排序并丢弃大量行，普通B-tree也无法支持包含搜索。应改为稳定 `(heat_score,updated_at,object_route_id)` 游标、单独的精确ID通路和受控全文/三元组名称索引；总数可改为按需或估算。

## 热度队列终止与重试风险

- 项目和评论热度任务失败后只清空锁并指数退避，attempt没有最大值、failed/dead-letter状态或人工重试边界；重试UPDATE错误还被直接忽略（`OPS-010`）。永久数据错误会使任务无限循环并持续写日志，运维无法区分暂时故障和毒任务。应采用有上限的持久状态机、记录最后错误和可审计重放，并监控失败/积压年龄。

## 搜索全量重建的内存和查询放大

- Typesense重建会先把当前集合全部文档加载成Go `[]map[string]any`，包括正文Markdown、多语言正文和多个字符串数组，完成后才按500条上传；项目查询还为每行执行本地化、标识、作者、标签和兼容性等多条相关子查询（`PERF-037`）。十万至百万项目/资料时，重建峰值内存接近整个索引原始内容并伴随数据库内部N+1式聚合。应按稳定ID游标从数据库流式读取/导入，在SQL中集合预聚合或分批联接，并设置重建资源预算和进度。
- 若任意一个集合永久失败，`projectionsCurrent`整体返回false，下一次重建不会跳过已经是当前版本的其他集合；成功集合也会每15秒反复全量重建并产生新集合。该放大与 `OPS-011` 的无分布式重建所有权叠加。

## 基础设施死信后台的历史可达性

`PERF-038`：死信列表固定按 `created_at desc limit 100` 返回且没有游标、offset或状态筛选。死信累计超过100条后，较旧但仍未处理的记录无法从管理界面定位和重放；这不是单纯展示限制，而会阻断运维恢复。应使用 `(created_at,id)` 稳定游标、状态/aggregate筛选和受控页大小，并保持单条重放事务锁。

## MRPack预检的同步外部请求放大

`PERF-039`：每次预检都在HTTP请求内下载Fabric loader目录或完整Forge/NeoForge Maven metadata（上限16MiB、超时30秒）；正式创建又完整执行同一预检并再次下载。没有按来源ETag/TTL缓存、没有站内具体加载器版本快照，也没有把预检选择绑定到创建。并发用户会把相同外部文档和解析成本线性放大到请求goroutine。应由受控同步任务维护权威加载器版本快照，预检和创建引用同一有版本快照；远端刷新使用条件请求、共享缓存与并发上限。

## 收藏夹导出依赖解析N+1与历史上限

`PERF-040`：`appendFavoriteExportDependencies` 对每个已导出项目/新依赖逐条查询依赖关系，再逐条加载候选文件；传递遍历最多100个节点。大收藏夹在正式创建前会产生近百次串行数据库往返和重复文件选择，硬上限又把扩展性问题转换为静默缺依赖（`BUG-066`）。应批量加载整个可达依赖图、一次选择候选并显式报告超限或循环。

`PERF-041`：用户导出历史固定读取最新100条，没有游标、页大小或总量协议，也不检查 `rows.Err()`。历史增长后旧报告不可达，前端无法满足长期查看和按相同设置重建的需求。应使用稳定 `(created_at,id)` 游标与受控页大小。

## 蓝图处理与材料详情

- `PERF-042`：单个蓝图允许16,777,216体积、8,000,000非空气方块、512 MiB源对象和256 MiB解码流。规范化会同时持有方块切片、材料map、渲染map和排序切片，并逐材料INSERT；公共转换又没有共享并发/用户预算。该上限在并发下不是可控服务边界，应按测得的每方块内存成本收紧、分块/流式处理并批量写入。
- `PERF-043`：一个蓝图详情的材料装饰会读取全站所有 `source_namespace` 的最新导入revision，而非只查询该蓝图实际使用的namespace。目录历史增长会直接放大公开详情热路径，应先收集namespace数组并用匹配索引限定SQL。

`PERF-044`：OSS预签名对用户执行当日源大小与全部活动存储SUM，完成时再执行一次全部活动存储SUM。即使有 `(uploader_id,created_at)` 索引，单用户百万文件仍需扫描和聚合大量记录；应改成原子额度桶并用离线SUM对账。
# 评论深页与观察列表（PERF-045、PERF-046）

根评论、直接回复和我的插眼都把`cursor`当整数OFFSET；根列表还在每次请求COUNT目标全部评论。百万级热门目标下，深页排序和丢弃成本随页码增长。更严重的是插眼列表逐条调用完整评论装配和目标解析，一页100项会形成数百次数据库/签名操作。应改成稳定keyset cursor、可校准计数，并批量解析评论、目标、权限、附件和头像。

公开thread端点无节点上限，最多深度256并不限制横向宽度；一个高分支树可以在一次匿名请求中完整加载和序列化，应改为定位邻域+分页并设置响应预算（`SEC-033`）。

## 皮肤库和玩家档案（PERF-047 至 PERF-049）

玩家档案列表逐档案加载纹理，权限上限100时形成101次查询。公共皮肤搜索把tags数组转字符串并对名称/描述执行前导通配符，同时使用OFFSET和同步COUNT；现有普通目录/GIN tags索引不能覆盖该搜索表达式。个人衣柜又一次返回最多5000个完整对象。应批量加载档案纹理、统一搜索基础设施和keyset分页，并把衣柜压到小页响应。

## 后台权限目录与用户列表N+1（PERF-062）

`roles()`先读取全部角色，再为每个角色单独查询权限；角色数量没有API上限。`adminUsers`虽限制100用户，却逐用户调用完整权限解析，最坏形成一次用户查询加100次缓存/数据库权限加载，而同包已有批量`resolveUsersRootPermissions`。后台权限管理在角色/用户增长时会产生线性往返，并放大Redis故障时的数据库压力。应一次加载全部角色权限、一次批量解析当前页用户，同时保留每页上限和可测SQL预算。

## 评分和基础收藏夹（PERF-050、PERF-051）

- 评分明细每页先精确COUNT，再按 `updated_at,id` 排序并使用OFFSET；百万评价热门项目的深页成本随offset增长。应使用 `(updated_at,id)` keyset游标，并把总数改为按需或投影值。
- 收藏夹列表、本人/公开收藏项都没有limit或游标；数据库也没有每用户集合/条目上限。当前Mod目录为了恢复收藏状态还会先取全部集合，再为每个集合各请求一次完整条目列表。仅基础API就需要分页与摘要，目录状态应由单个批量membership接口返回。

## 社区内容目录与引用写入（PERF-052、PERF-053）

- `PERF-052`：社区目录每项读取完整 `body_markdown`（单篇允许1 MiB），一页最多100篇；数据库回退搜索对标题和正文执行前导通配符，随后重复一遍同条件精确COUNT，并允许任意深整数OFFSET。高内容量目录会同时放大数据库扫描、网络响应和Go堆内存。列表应返回摘要/截断正文，使用统一搜索索引、keyset游标和按需计数。
- `PERF-053`：项目/小型资料引用数组没有数量或单项长度上限；8 MiB请求内可放入大量条目。解析阶段逐引用查询目标，保存阶段又逐引用INSERT并为未解析项逐条UPSERT，形成约2N至3N次串行SQL和长事务。应设置领域上限、批量解析和批量写入，未解析引用也应批量去重。

## 内容修订历史与差异存储（PERF-054、PERF-055）

- `PERF-054`：社区内容和Mod资料资源历史查询没有limit、cursor或服务端最大条数；资源历史还会分别全量读取人工修订和导入快照后在Go中合并排序。长期活跃对象会产生无界数据库扫描、内存和响应。
- `PERF-055`：每个新修订先解码完整前后JSON，再递归比较。对象每个变化叶子执行一次单独INSERT；数组被视为单一值，在`content_change_items`中再次完整保存before与after。大资源数组会在已经保存完整revision快照之外重复保存两份，并扩大事务锁持有时间。应采用批量插入和有预算的结构化patch/摘要，对超大数组避免全值三重持久化。

## 等级配置全站重算（PERF-056）

管理员每次保存等级阈值都会在一个事务中`select user_id,experience from user_experience for update`锁住全表，再逐用户UPDATE等级并逐用户查询轨道角色、DELETE/INSERT角色。用户达到百万级时，这是O(users × track SQL)的长事务和大锁范围，会阻塞经验奖励与权限变化。配置保存应只提交新版本并建立可恢复的分批重算任务；基于游标领取批次、记录进度，并保证新旧配置切换期间权限语义明确。

## 表情引用检查和目录规模（PERF-057）

删除单个表情时，以`position(token in markdown)>0`串联9个`exists`扫描；普通B-tree/GIN全文索引均不能有效支持这种任意子串条件。评论、项目和历史达到百万级时，单次后台删除可能顺序扫描多张大表，而且当前查询仍漏掉多套Markdown存储。公开目录和后台目录也没有包/表情数量上限或分页，全部装入内存并返回。应在写入时解析Token并维护`sticker_content_references`等结构化引用表（含当前/历史来源及唯一约束），删除走索引化引用；同时为管理目录分页并给公开目录配置总量预算/版本缓存。

## 站点更新日志深分页（PERF-058）

公开更新日志使用`LIMIT/OFFSET`，没有游标或总量上限；`boundedOffset`只防负数，不限制深度。十万至百万条记录时深页需要扫描并丢弃前序行。后台列表反向固定`limit 100`且没有分页，较旧记录无法管理。应使用`(change_date,id)`稳定游标，后台与公开端共享分页模型；若业务只永久展示少量记录，也应配置可验证的保留/上限而不是隐式截断。

## 未解析引用搜索与计数（PERF-059）

列表先`UNION ALL`两套引用，再对`raw_identifier/source_label ILIKE '%q%'`过滤、执行`count(*) over()`并按时间排序，最后OFFSET分页。前导通配无法使用普通索引；每一页都计算全部匹配总数，深页再丢弃前序结果。十万至百万待处理引用时会形成高CPU/IO后台查询。应以`created_at/id`游标分页，把总量改为独立可选统计或维护状态计数；关键词若必须子串搜索，使用受控trigram索引并限制查询长度/频率。

## 举报历史与小黑屋分页（PERF-060）

本人举报、审核队列和小黑屋全部使用整数OFFSET且没有最大深度；审核队列与小黑屋至少有状态/时间顺序索引，但本人举报查询`where reporter_id order by created_at desc,id desc`没有对应完整索引，现有部分唯一索引只覆盖待处理状态且列顺序服务去重而非历史排序。前端审核面板完全不发送offset/limit和翻页，只能访问每个状态最前50条；封禁面板固定取前100条。百万举报或长期小黑屋下既会深页丢弃，也会让旧记录在当前UI不可达。三类列表应使用`(created_at,id)`稳定游标、增加本人举报复合索引并提供前端分页；总数若需要应独立按需读取，不放进每页热查询。

维护Worker将举报证据、封禁、日志分享、草稿、Yggdrasil与Presence的所有过期数据串行放入同一个30秒context。每类会在清空前一批积压前不让出，因而第一类持续超载时后续TTL清理即使有高效索引也不会执行（`OPS-020`）。应使用分类时间/批数配额和公平轮转，对封禁等安全状态单独调度。

草稿列表不返回大payload，但`GET /users/me/drafts`仍无limit/游标返回当前用户全部未过期活跃和已完成记录。在无存量配额的写入模型下，用户可自行将它放大为大排序、大响应和大DOM（`SEC-043`、`PERF-061`）。应以派生状态时间+ID游标分页，并先在写入端建立原子条数/字节上限。

## 前端大文件哈希与资料全集装载（PERF-063、PERF-064）

- 所有通用OSS上传会在multipart前执行`File.arrayBuffer()`和一次性WebCrypto SHA-256。分片网络上传因此仍需在主页面上下文完整物化大文件；多文件并发或移动设备的峰值内存不可控。应采用有界分块哈希Worker、限制并发，并把取消信号覆盖哈希阶段。
- `loadAllModContentSectionResources`固定请求最多20000条并循环聚合到单个数组，普通资料板块、工作区和布局编辑器共同使用。后端每行又解析本地化、图标、导入快照和详情状态。应把公共列表改为稳定游标/虚拟化，把布局与进度图改为专用轻量摘要和增量提交；对1万与2万行执行真实SQL计划和浏览器内存/帧率测试。

## 目录资源图标缓存（PERF-065）

`CatalogResourceIconValue`用模块级Map按`资源标识 + locale`永久缓存成功的完整资源展示DTO，只有失败请求会移除。长时间后台目录编辑、经济记录和主页浏览可不断加入新键，八种语言还会分别占用条目；缓存没有容量、TTL或服务端修订失效语义。应复用受控查询缓存或实现小型LRU/TTL，在保留并发请求合并的同时限制浏览器会话内存与陈旧图标。

## 公开日志全文传输与浏览器物化（PERF-066）

日志公开详情在一次数据库查询和JSON响应中返回分享内所有条目的完整脱敏正文。前端只截断实际渲染到150万字符，但完整正文已经经过数据库、Go堆、JSON、网络和React状态；搜索还会对全文按行切分。大日志和ZIP因此没有真正的分块读取边界。应让详情返回条目元数据/首块预览，正文使用受限Range或游标块，并给服务端搜索、下载重建和并发公开读取设置独立资源预算。

## 审核队列逐项装配（PERF-067）

项目编辑员申请在读取一个状态的全部记录后逐项查询目标名称；服务器审核固定取200条后，又为每条分别读取证明文件、链接和模组，最坏为`1+3N`次数据库往返。两个后台组件均没有服务端分页。应使用稳定游标限制一页规模，并按当前页ID批量读取所有关联数据；需要用查询计数测试保证一页SQL次数不随条目数量线性增加。服务器队列的固定窗口还会让第201条后的申请不可达（`BUG-139`）。

## 资源选择器预选项补全N+1（PERF-068）

通用资源选择器会为每个未解析或缺少展示名称的预选项分别发起一次搜索请求，最多只是用6个worker限制并发；请求总量仍是N，并会在locale变化时重新执行。项目、依赖和合成候选数量增长后，打开编辑对话框就会把网络与数据库查询线性放大。应提供按公开ID/规范标识批量解析的轻量接口，并按资源修订和locale缓存展示快照，而不是用完整分页搜索逐项水合。

## 蓝图浏览器对象放大与不可取消构建（PERF-069、PERF-070）

- `PERF-069`：前端允许最多600,000个可见方块，但场景构建按每个模型Mesh分别保存方块数组，并为每个实例克隆一个`Matrix4`；普通六面立方体会把CPU对象按面放大。楼层切换随后逐Mesh全量遍历、重写实例矩阵和重算包围盒。GPU实例化只降低draw call，没有给JS堆和交互主线程提供真实预算。应以TypedArray和共享位置索引保存一次方块数据，按层预分桶，并用实测内存/帧时间共同确定上限。
- `PERF-070`：加载代次只在完整场景构建后丢弃过期结果，资源读取、模型解析、矩阵生成和包围盒计算都没有`AbortSignal`。快速切换或卸载会让旧大任务继续与新任务竞争资源。取消信号需要贯穿资源源和构建循环，并在中止时精确释放中间Three.js对象。

## 资料布局编辑器平方级派生计算（PERF-071）

资料布局页面已通过`loadAllModContentSectionResources`装载最多20000条完整资料（`PERF-064`），渲染时又为每个分类过滤整份资源数组，并在每个分类内为每项执行`findIndex`。一个含2万项的平铺分类会产生平方级比较，受控输入、选择和拖拽触发的重渲染会重复这组计算。应一次按分类分组并预建索引，使用修订依赖的memo；长期应改为轻量布局DTO、虚拟化和增量编辑协议。
