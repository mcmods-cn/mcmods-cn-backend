# OSS activity boundaries and recovery

The upload ticket producer prepares the signed PUT/multipart capability before acquiring database locks. One transaction then saves the pending private blueprint and localization, exact source reservation, multipart session and **existing** request activity. Its response discloses the capability only after commit. Known-file cover binding, orphan blueprint association and existing activity likewise commit together. The reusable-file path still applies actual verified-source hashing and current raster/ownership rules. Upload/complete actions keep their original classification; this change does not add a task, reward definition or permission.

If ticket persistence fails, no ticket is issued. A multipart upload created by that attempt is aborted outside database locks. If its provider is unavailable, a durable `cleanup_pending` session preserves only the failed attempt's cleanup target, without a quota reservation, blueprint or activity/reward. The existing cleanup worker retries it. A process interruption before a remote upload ID is returned cannot record that unknown ID; the already required provider lifecycle rule aborts unissued multipart uploads within seven days. No database transaction can roll back a remote provider operation.

The three administrator replay routes preserve their existing create/file activity classification, public job identifiers, access control, generation/lease rules and security audit. Queue state, replay count, security audit and original activity now share the replay transaction. A repeated replay of a job that is no longer dead remains a conflict and emits no second intent. User deletion was independently fixed in commit98810a7: file tombstone, reference checks, quota accounting, deletion intent and existing activity share its transaction. Signed download tickets prepare their URL outside locks, then commit the established counter and original route activity together before disclosing it; the POST classification is preserved rather than redefining the reward policy.

`go run ./cmd/audit-known-data --since <RFC3339> --until <RFC3339> --limit 100` is read-only and bounds every sample. It emits counts and public IDs for missing report-evidence metadata candidates, expired quota reservations and dead cleanup/rehome/deletion jobs. It also counts historical files for which the old schema has no exact activity linkage. **That set is not a missing-reward count.** File creation times, an upload status or a best-effort operational log do not prove the original successful request event, reward eligibility or whether an event was already consumed. Neither the tool nor the repair automatically credits balances/XP or reconstructs a historical event from those fields.

A legitimate uploader's repeated completed report-evidence request can repair its missing metadata only after rechecking the immutable owner/object/source/hash/size identity; it creates no guessed upload reward. The new atomic orphan-blueprint association preserves existing files and shared references. Dead jobs use the authorized replay API, preserving the prior audit. These are factual repairs; historical currency/XP compensation requires independently corroborated exact request and event evidence, duplicate reconciliation and explicit approval. Production diagnosis or repair has not been executed in this task.
